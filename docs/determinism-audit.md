# Аудит источников недетерминизма (`core`)

Документ подготовлен в рамках **Задания 3** ТЗ `trumpcards_review_and_refactor.md`.

Цель: перечислить каждое место в `core`, где потенциально может появиться
платформенная или скрытая недетерминированность, и по каждому дать **вердикт**
(«безопасно, потому что…» либо «фикс»). Сверка с `GameSimulator`-тестами,
golden-сценариями (`GoldenScenarioTest`), воспроизводимостью событий
(`ReplayDeterminismTest`) и round-level replay (`RoundLevelSimulatorTest`).

Проверено на текущем (до Задания 4) коде. Все выводы подтверждены тестами,
зелёными в `./gradlew :core:test`.

## 1. Перечень источников и вердикты

| # | Место | Что может быть недетерминированным | Вердикт |
|---|---|---|---|
| 1 | `SplitMix64()` default ctor → `SEED_COUNTER = new AtomicLong(System.nanoTime())` | `System.nanoTime()` как стартовое зерно | **Безопасно (ожидаемо).** Единственный источник платформенной недетерминированности; проявляется только если игру не засеять. Тесты обязаны инжектировать `Rng` (`setRng`/`playGame(rng)`) или `ScriptedCardDealer`. |
| 2 | `Game.chooseFirstDealer()` → `rng.nextInt(players.size())` | Потребляет один draw из RNG **до** шаффла | **Безопасно, но это часть контракта.** Порядок обращений к RNG (дилер → шаффл) фиксирован; вставка лишнего `nextInt` изменит все партии по сиду. Задокументировано здесь (см. §3). |
| 3 | `Game.distributeObligatoryCards()` → `ownerBySuit` (`java.util.HashMap`) | Порядок обхода `HashMap` | **Безопасно.** Внешний цикл идёт по `players` (`TurnOrder` — детерминированный список), `ownerBySuit` используется только через `get(suit)`. Порядок `HashMap` на результат не влияет (см. §2). Рекомендация: заменить на `EnumMap` для однозначности. |
| 4 | `Game.snapshotHands()` (`java.util.HashMap`) | Порядок обхода при рендере `RoundStarted` | **Безопасно.** Map только кладётся в событие; `Map.equals` порядок-независим, а `EventLog` канонизирует вывод по порядку объявления `Card.Suit`. |
| 5 | `GameSimulator.runOne()` → `new HashSet<>(allCards)` | Порядок обхода `HashSet` | **Безопасно.** Используется только `size()` (проверка отсутствия дубликатов). |
| 6 | `Scoreboard` → `EnumMap`/`ArrayDeque` | — | **Безопасно.** `EnumMap` детерминирован (порядок объявления), deque — по вставке. |
| 7 | `TurnOrder` | «Случайный якорь» из старой реализации | **Безопасно.** Обычный `ArrayList`, круговой обход детерминирован. |
| 8 | `Dealer.shuffle(Rng)` (Fisher-Yates) | Зависит от RNG | **Безопасно** при инжектированном `Rng`: один и тот же поток → один и тот же порядок. |
| 9 | `Player.validDefenses` / `AiDecisionStrategy` | Порядок сортировки | **Безопасно.** `Comparator` полностью задан (trump-флаг, затем ранг); `min` детерминирован. |
| 10 | `Game.endRound()` → `pile.stream().min(by rank value)` | Тай-брейк минимума | **Безопасно.** В руке+банке не бывает двух карт одной масти с одинаковым рангом (инвариант уникальности), ничьих нет. |
| 11 | `Math.random()`, `ThreadLocalRandom`, `new Random()`, `parallelStream()` | — | **Отсутствуют.** Поиск по `core/src/main` не находит вхождений. |
| 12 | `System.currentTimeMillis()`/`nanoTime()` в игровой логике | — | **Отсутствуют**, кроме п.1 (`SplitMix64` seed counter). |
| 13 | `ScriptedCardDealer` (тест) | — | **Безопасно.** RNG игнорируется; порядок заливки задаётся `fillOrder`. |

**Итог:** в игровой логике `core` скрытой недетерминированности не найдено.
Единственный платформенный источник — дефолтное зерно `SplitMix64` (п.1), которое
обязано быть перекрыто в тестах. Порядок потребления RNG (п.2) — часть контракта.

## 2. Подтверждение по `ownerBySuit` (HashMap)

`Game.distributeObligatoryCards()`:

```java
Map<Card.Suit, Player> ownerBySuit = new java.util.HashMap<>();
for (Player p : players) ownerBySuit.put(p.getTrump(), p);   // порядок записи = TurnOrder
...
for (Player current : players) {                              // внешний цикл — стабильный список
    for (Card card : current.getHand()) {                     // порядок руки — по вставке
        ...
        if (card.rank() == required) transfers.add(new Transfer(current, card, ownerBySuit.get(suit)));
    }
}
for (Transfer t : transfers) { ... }                          // порядок transfers — от players+hand
```

Порядок обхода `HashMap` **не участвует** в формировании результата:
- внешний цикл — по `TurnOrder`;
- обращения к `ownerBySuit` — только `get(suit)` (без итерации);
- список `transfers` формируется в порядке `players` и рук.

Карты одной масти уникальны, а переводы не пересекаются по источнику (каждая карта
обрабатывается один раз), поэтому итоговое состояние рук не зависит от порядка
применения `transfers`. **Вердикт: детерминировано.** Замена на `EnumMap`
(улучшение читаемости, не фикс бага) выполнена: `ownerBySuit` и `snapshotHands`
теперь `new EnumMap<>(Card.Suit.class)`.

## 3. Контракт порядка потребления RNG (D3)

За одну партию RNG потребляется в следующем порядке:

1. `chooseFirstDealer()` — ровно один `nextInt(players.size())` в начале игры
   (`GameDriver.startGame()`, до первого шаффла).
2. `shuffleAndDeal()` каждого раунда — `Dealer.shuffle(rng)`: Fisher-Yates,
   `i` от `pool.size()-1` до `1`, то есть ровно `pool.size()-1` вызовов
   `nextInt(i+1)`. Затем `Dealer.deal(...)` — RNG **не** используется (раздача
   round-robin детерминирована).

Здесь `pool` — текущий пул колоды на старте раунда (в первом раунде это 36 карт
минус 4 базовые карты на табло; далее — карты, возвращённые `endRound`), поэтому
размер пула меняется от раунда к раунду.

Следствие: **любая вставка дополнительного обращения к RNG (или изменение размера
пула между вызовами) сдвинет всю последовательность и изменит результат для всех
seed'ов.** Это зафиксировано, чтобы будущие правки не «сломали детерминизм» незаметно.
Воспроизводимость проверяется `ReplayDeterminismTest` (побитовое равенство потока
событий для фиксированных seed'ов, включая патологический).

### 3.1. Дефолтное зерно `SplitMix64()` (D4)

`SplitMix64()` без аргумента берёт зерно из
`SEED_COUNTER = new AtomicLong(System.nanoTime())` (плюс монотонная добавка
`0x9E3779B97F4A7C15L`), поэтому **две незасеянные партии всегда различаются**. Это
ожидаемое поведение продакшена и единственный платформенный источник
недетерминированности в `core` (см. п.1 таблицы §1). Контракт:

- детерминизм гарантируется **только** при явной инъекции `Rng`:
  `new Game(...).setRng(rng)`, `playGame(rng)` либо `Game.restore(saved, ...)`
  (seed восстанавливается из `SavedGame.rngSeed()`);
- в тестах вместо незасеянного `SplitMix64()` используется `determinism.FixedRng`
  или `ScriptedCardDealer` — обязательное правило для любого нового теста.

## 4. Найденные дефекты и расхождения (не исправлены)

> По требованию Задания 3 реальные баги/расхождения фиксируются отдельно и **не
> смешиваются молча** с рефакторингом. Ничего из перечисленного ниже не менялось.

### 4.1. Устаревший комментарий про seed 0 (`Game.MAX_ROUND_MOVES`) — **ИСПРАВЛЕНО**

Javadoc `MAX_ROUND_MOVES` утверждал: «e.g. seed 0 loops 2M+ moves». Проверка
(`GameSimulator`) показывает, что **seed 0 больше не патологический**: 31 раунд,
`cappedRounds = 0`, завершается штатно (~92 мс). Причина расхождения — эволюция
движка/AI после написания комментария.

**Реальные патологические seed'ы** (из сканирования `[0..49999]`, ровно по 1
капнутому раунду): **12129, 24847, 30649, 49128**.
**Фикс:** комментарий в `Game.MAX_ROUND_MOVES` обновлён на актуальные seed'ы и на
факт «seed 0 не патологический». 12129 используется в тестах капа
(`ReplayDeterminismTest`/`RoundLevelSimulatorTest`).

### 4.2. NPE при наборе игроков, не покрывающем все 4 масти — **ИСПРАВЛЕНО**

Изначально `Game.distributeObligatoryCards()` строил `ownerBySuit` только из
фактических `players`. Если игрок держал SEVEN масти, владельца которой нет за
столом (например, игра на 2–3 места), `ownerBySuit.get(suit)` возвращал `null`,
и `t.to().addCard(...)` бросал `NullPointerException`.

**Фикс:** перевод пропускается, если `ownerBySuit.get(suit) == null` — карта
остаётся у владельца (у несуществующего владельца нет, кому передавать). Поведение
для штатных 4-местных составов не изменилось; изменение затрагивает только
произвольные наборы через `public Game(List<Player>)`.

**Тест:** `GameTest.distributeObligatoryCards_incompletePlayerSet_skipsUnownedSuits`
(2 места; передача «своих» SEVEN работает, а SEVEN несуществующей масти остаётся
на месте, карты сохраняются). Дополнительно `ScriptedCardDealer` научен игнорировать
пустые «лишние» руки для отсутствующих мастей.

### 4.3. Тай-брейк при лимите ходов (`rules.md` §8)

`rules.md` §8: при достижении лимита 10000 ходов проигрывает игрок с наибольшим
числом карт, **при равенстве — случайно**. Код (`RoundResolver.mostCards(players)`) выбирает
максимум и **при равенстве — первого по кругу** (детерминированно), случайного
выбора нет. Это расхождение с текстом правил; для воспроизводимости детерминизм
даже полезен, но формально расходится с source-of-truth.
**Предложение:** согласовать с заказчиком: либо обновить `rules.md`, либо
задокументировать детерминированный тай-брейк как уточнение.

### 4.4. Расхождение формальной модели и реализации по RNG — **ИСПРАВЛЕНО**

`docs/game_state_machine.yaml` описывал LCG («Linear Congruential Generator»),
тогда как реализация использует `SplitMix64`. На детерминизм не влияет (оба
детерминированы), но модель вводила в заблуждение.
**Фикс:** RNG-блок YAML переписан под `SplitMix64` (алгоритм `nextBits` +
rejection sampling в `nextInt`), тип состояния `rngState` изменён на `long`.
