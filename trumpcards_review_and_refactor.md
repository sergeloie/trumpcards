# ТЗ для агента: код-ревью, детерминированное тестирование и рефакторинг `trumpcards`

Репозиторий: https://github.com/sergeloie/trumpcards
Модули: `core` (доменная логика игры, чистая Java), `console`, `desktop-libgdx`, `android` (UI-порты), `docs`.
Сборка: Gradle (`./gradlew :core:test` — тесты домена).

## 0. Важный контекст, который агент должен учитывать с первого шага

Код `core` уже прошёл через несколько предыдущих итераций рефакторинга — это видно по javadoc-пометкам вида `refactor Stage 4`, `Stage 7`, `(R2)`, `(R5)`, `(R6)`, `(R10)` в `Game.java`, `Dealer.java`, `TurnOrder.java`, `Scoreboard.java`. Уже реализовано:

- `Rng` — интерфейс ГПСЧ с сериализуемым состоянием (`SplitMix64`), внедряется в `Dealer.shuffle(Rng)` и в `Game` (`setRng`, `playGame(Rng)`), есть тестовый seam `Game.shuffleAndDeal(Rng)`.
- `DecisionStrategy` — единый интерфейс выбора хода (`chooseLeadCard`, `chooseDefenseCard`), с реализациями `AiDecisionStrategy` (чистая, детерминированная) и `HumanDecisionStrategy` (делегирует в `InputProvider`). `Player` не знает, откуда берётся решение.
- `GameDriver` (внутренний класс `Game`) — пошаговый движок с sync/async режимом ввода человека, сохранением/восстановлением (`SavedGame`).
- `GameSimulator` — прогоняет много игр по seed'ам и проверяет инварианты (сохранение карт, единственный победитель, детерминизм по seed, попадание в защитный лимит `MAX_ROUND_MOVES`).
- Тесты: `DealerTest`, `GameSimulatorTest`, `GameDriverTest`, `GameDriverAsyncTest`, `GameSerializationTest`, `ScoreboardTest`, `GameStateTest`, `HumanPlayerStage1Test`.

**Прежде чем что-либо менять, агент обязан:**
1. Прочитать весь `core` целиком (не только сигнатуры — реализацию), включая javadoc с пометками R1–R10 и Stage N — это зафиксированные архитектурные решения и инварианты предыдущих итераций, их нельзя случайно откатить.
2. Прочитать `rules.md` — он является source of truth по игровым правилам. Любое найденное расхождение между кодом и `rules.md` фиксируется отдельно как находка, а не тихо "исправляется" по своему усмотрению.
3. Не менять реальную игровую логику (кто кого бьёт, кто забирает банк, правило обязательной передачи карт, правило выбывания по тузу) ни на одном из этапов ниже, кроме случаев, когда расхождение с `rules.md` явно согласовано отдельно.

Работы выполняются строго в порядке: **Задание 1 → Задание 2 → Задание 3 → Задание 4**. После каждого коммита `./gradlew :core:test` должен быть зелёным.

## Задание 1 — Код-ревью проекта

**Объём:** весь репозиторий; `core` — полная глубина, `console`/`desktop-libgdx`/`android` — по одному критерию: не дублируют ли они игровую логику, которая должна жить только в `core`.

**Результат — файл `docs/review.md`** со следующими разделами:

1. **Карта архитектуры**: модули и их зависимости, кто на кого ссылается, где домен утекает наружу (например, ссылается ли `core` на что-то платформенное, знает ли UI-слой о внутренностях `Game`, кроме `GameState`/`GameDriver`/`SavedGame`).
2. **Реестр находок**, для каждой — файл/класс/метод, описание, категория и серьёзность:
   - риски для корректности правил игры;
   - дублирование логики;
   - скрытая связность (два места должны меняться синхронно, но это нигде не оформлено явно);
   - утечки инкапсуляции (публичный метод отдаёт изменяемую внутреннюю коллекцию, хотя рядом заявлен принцип неизменяемых snapshot'ов);
   - неоднозначность/нечитаемость (методы, делающие больше одной вещи; неймспейсы, где не сразу понятно, что откуда берётся);
   - пробелы в тестовом покрытии;
   - потенциальные проблемы потокобезопасности (в `Game` явно задокументирован контракт "не потокобезопасен, мутировать только с engine-потока" — проверить, что нигде в UI-портах это не нарушается).
3. **Обязательно явно ответить на вопрос:** действительно ли `DecisionStrategy` — это *единственная* точка, через которую определяется ход и человека, и бота, или есть места, где `GameDriver`/`Game` ветвятся по `isHuman()`/`asyncInput` и параллельно реализуют часть игровой логики отдельно от `Player.makeMove()` (см. подсказку в Задании 4, п. 2 — но агент должен найти это сам в рамках ревью, а не просто списать формулировку).
4. **Приоритизированный бэклог** находок (Критично / Важно / Желательно), с грубой оценкой трудозатрат — он ляжет в основу Задания 4.

## Задание 2 — Вынести тасовку и раздачу карт за интерфейс, инжектируемый в тестах

**Проблема.** Сейчас детерминизм раздачи достигается только через `Rng`-сид: `Dealer.shuffle(rng)` + `Dealer.deal(...)`. Чтобы в тесте узнать, какие именно карты получит каждый игрок, нужно реализовать/просчитать сам алгоритм `SplitMix64` под конкретный сид — это непрямой и хрупкий способ. Нужно, чтобы тест мог **напрямую задать**, какие карты окажутся в руке у каждого игрока, не трогая ГПСЧ вообще.

**Что сделать:**

1. Выделить интерфейс раздачи, например:

   ```java
   public interface CardDealer {
       /** Строит и перемешивает колоду (или готовит уже заданный порядок). */
       List<Card> prepareDeck();

       /** Раздаёт карты активным игрокам, начиная с левого от dealer. */
       void deal(TurnOrder order, Player dealer, Predicate<Player> active, List<Card> deck);
   }
   ```

   Либо разделить на два меньших интерфейса (`DeckSource` — что раздавать, `Dealing` — как раздавать по кругу), если так будет чище с учётом существующего `Dealer`. Итоговую форму интерфейса агент выбирает сам, но обязательные свойства:
   - существующий класс `Dealer` (с реальным перемешиванием через `Rng`) становится одной из реализаций интерфейса — поведение прода не меняется по умолчанию;
   - `Game`/`GameDriver` перестают быть жёстко связаны с конкретным классом `Dealer`, а зависят от интерфейса (внедрение через конструктор и/или сеттер, по аналогии с уже существующим `setRng`);
   - `Dealer.deck()` сейчас отдаёt наружу живой мутируемый `List<Card>` (`return deck;`) — это несовместимо с остальным принципом неизменяемых snapshot'ов в проекте (R5). Поправить заодно при выделении интерфейса.

2. Добавить тестовую реализацию **`ScriptedCardDealer`** (или аналогичное имя) в `core/src/test/...`:
   - конструируется из явной раскладки `Map<Card.Suit, List<Card>>` — что у кого будет на руках после раздачи;
   - при вызове `deal(...)` кладёт игрокам ровно эти карты, без обращения к `Rng`;
   - валидирует на входе: все карты различны, суммарное количество совпадает с ожидаемым (колода минус карты, ушедшие на табло `Scoreboard` при инициализации), нет карт, которые обязаны быть в `Scoreboard`, а не в руках;
   - даёт понятный `IllegalArgumentException` при нарушении инвариантов, а не тихо портит состояние игры.

3. Убедиться, что дальнейший шаг `Game.distributeObligatoryCards()` (обязательная передача карт перед раундом) отрабатывает поверх raскладки от `ScriptedCardDealer` точно так же, как поверх настоящей раздачи — это не должно требовать отдельного кода.

4. Публичное API для теста: должна быть возможность написать что-то вроде

   ```java
   Game game = new Game(players, DeckSize.THIRTY_SIX);
   game.setCardDealer(new ScriptedCardDealer(Map.of(
       Card.Suit.SPADES, List.of(new Card(SPADES, SEVEN), ...),
       Card.Suit.HEARTS, List.of(...),
       ...
   )));
   ```//    — точная сигнатура на усмотрение агента, главное чтобы тест мог задать раздачу декларативно, без знания ГПСЧ.

**Приёмка Задания 2:**
- Новый интерфейс + продовая реализация (обёртка над текущим `Dealer`) + `ScriptedCardDealer` + модульные тесты на сам `ScriptedCardDealer` (в т.ч. на невалидные раскладки).
- `Game`/`GameDriver` используют интерфейс, а не конкретный класс, во всех местах, где раньше был жёстко зашит `Dealer`.
- Существующие `DealerTest` и остальные тесты остаются зелёными без изменений их ожиданий (поведение по умолчанию не менялось).

## Задание 3 — Приведение кода в однозначно тестируемое состояние + тесты воспроизводимости

**Цель:** гарантировать, что для одной и той же входной раскладки/сида результат **каждого раунда** (не только итог всей партии) детерминирован и не меняется от прогона к прогону — это главная защита от того, что LLM при последующих правках случайно исказит игровую логику.

1. **Аудит источников недетерминизма.** Пройтись по `core` и явно перечислить (в `docs/determinism-audit.md`) каждое место, где потенциально может появиться платформенная/скрытая недетерминированность: обычные `HashMap`/`HashSet` вместо `EnumMap`/`LinkedHashMap` там, где порядок обхода мог бы повлиять на результат (пример для проверки — `ownerBySuit` в `Game.distributeObligatoryCards()`, использующий `java.util.HashMap`: убедиться, что порядок обхода `players` в внешнем цикле, а не порядок `HashMap`, определяет результат; если это не так — исправить), использование `System.currentTimeMillis()/nanoTime()`, `Math.random()`, недетерминированного `Random` вместо инжектируемого `Rng`, зависимость от порядка `Set`/итерации потоков (`Stream`) с параллелизмом и т.п. По каждому пункту — либо подтверждение "безопасно, потому что...", либо фикс.

2. **Новый пакет тестов `ru.anseranser.model.determinism`** (или расширение существующих файлов, если так удобнее агенту), включающий:
   - **Golden/сценарные тесты**: несколько (минимум 4–6) написанных вручную раскладок через `ScriptedCardDealer` из Задания 2, с зафиксированными детерминированными `AiDecisionStrategy` на всех местах, где явно прогоняется полная партия или отдельный раунд, и **жёстко закреплённым ожидаемым результатом** (кто проиграл раунд, какая карта ушла на табло, кто выбыл, кто выиграл партию). Эти тесты — не просто "детерминизм", а прямая проверка соответствия `rules.md`: раскладки нужно подбирать так, чтобы явно проверить обязательную передачу карт, взятие банка при невозможности отбиться, выбывание по тузу, лимит `MAX_ROUND_MOVES`.
   - **Тест на воспроизводимость по раундам для seed-режима**: один и тот же `SplitMix64(seed)` прогоняется дважды через `GameDriver`, при этом через тестовый `GameListener` собирается полная последовательность событий (`GameEvent.RoundStarted/RoundEnded/...`) за оба прогона — списки должны быть побитово равны. Сделать для нескольких seed'ов, включая как минимум один из "патологических" (например, seed 0, упомянутый в комментариях `Game` как зацикливающийся и упирающийся в `MAX_ROUND_MOVES`) — на нём тоже должна быть воспроизводимость, а не просто "тест игнорируется".
   - **Round-level расширение `GameSimulator`**: сейчас `GameSimulator`/`GameSimulator.Result` проверяет только инварианты по итогу *всей* партии (сохранение карт, один победитель, детерминизм финального победителя). Добавить возможность собирать снимок результата **каждого раунда** (проигравший, вытолкнутая карта, флаг выбывания) и сравнивать эти списки между двумя независимыми прогонами того же seed на большом наборе seed'ов (сотни/тысячи) — не только итог, а весь путь партии совпадает бит-в-бит.
   - Убедиться, что все новые тесты быстрые (без сна/таймаутов) и не пишут во внешние ресурсы — пригодны для CI.

3. **Документ `docs/testing.md`**: как добавить новый golden-сценарий, какие инварианты обязаны оставаться зелёными в любом PR, трактовка "капнутых" (`cappedRounds`) партий.

**Приёмка Задания 3:** новые тесты явно проходят на текущем (до Задания 4) коде; если по ходу аудита найдены реальные баги/недетерминизм — они фиксируются отдельным списком с предложенным фиксом, но не смешиваются молча с остальным рефакторингом.

## Задание 4 — Рефакторинг `core`: убрать дублирование, неоднозначность, снизить связность, унифицировать интерфейс ходов

Ниже — обязательный минимум находок (по факту разбора `Game.java`, `Player.java`, `Dealer.java`); список нужно дополнить тем, что агент найдёт сам в Задании 1.

1. **`Game.java` — god-class (739 строк).** Содержит: оркестрацию раунда, snapshot'ы для событий, весь сериализационный код (`save()`/`restore()`), и вложенный класс `GameDriver` с отдельной параллельной state-machine для синхронного/асинхронного хода человека. Разбить на:
   - `RoundResolver` (или похожее имя) — вынести туда `countActiveGamers`, `countActiveGamersWithCards`, `mostCardsRounder`, `determineLoser`: сейчас это четыре отдельных цикла по `players` с очень похожей структурой (два из них, `mostCardsRounder`/`determineLoser`, различаются только критерием отбора) — унифицировать через один параметризуемый обход `TurnOrder` с предикатом/компаратором.
   - Сериализацию (`GameDriver.save()`, статический `Game.restore(...)`, дублирующиеся приватные `playerByTrump` — он объявлен и как метод экземпляра внутри `GameDriver`, и как статический метод в `Game`, с идентичной логикой) — свести в один компонент (например, `SavedGameMapper`), убрать дублирование `playerByTrump`.
   - Пересмотреть, насколько оправдано, что `GameDriver` — non-static inner class, читающий приватные поля `Game.this` напрямую (`Game.this.pot`, `Game.this.dealer`, `Game.this.scoreboard`, `Game.this.rng` и т.д.). Либо задокументировать и явно ограничить эту связность точечными пакетными методами доступа, либо вынести в отдельный класс с явно переданной зависимостью на `Game`/на новый вынесенный "внутренний контекст раунда".

2. **Единый интерфейс хода для человека и бота — проверить сквозную унификацию.** `DecisionStrategy` — правильная абстракция, но `GameDriver.step()` физически ветвится:
   - обычный путь: `current.makeMove(pot)` — там уже единообразно вызывается `strategy.chooseLeadCard/chooseDefenseCard`;
   - асинхронный человеческий путь: отдельный приватный метод `humanTurn()` внутри `GameDriver`, который **заново** реализует то же самое ветвление "банк пуст → веду карту / банк не пуст, есть чем отбиться → отбиваю / нечем — забираю банк", но напрямую вызывая `current.playLeadCard(...)`, `current.beatCard(...)`, `current.takePot(...)`, а не через `Player.makeMove()`.

   Итог: правило "что делать дальше" продублировано в двух местах (`Player.makeMove()` и `GameDriver.humanTurn()`), и это ровно тот риск, о котором просил заказчик — при следующей правке игровой логики легко поправить одно место и забыть про второе.

   **Требуемый рефакторинг:** свести оба пути к одному источнику истины. Например, разложить `Player.makeMove()` на набор мелких методов, описывающих "что за действие нужно сейчас" (`nextActionKind()` → LEAD/DEFEND/TAKE_POT) и "выполнить это действие с данной картой" (`applyLead(card)`, `applyDefense(card)`, `applyTakePot()`), и заставить **и** `makeMove()`, **и** `GameDriver` (в обоих режимах, sync и async) пользоваться этими же методами. `GameDriver` должен отвечать только за *паузу/возобновление* и подписку карты из `resume(Card)`, но никогда сам не решать, какое действие сейчас легально — это должно проверяться в одном месте в `Player`.

3. **Инкапсуляция:** `Dealer.deck()` возвращает "живой" изменяемый список — привести к тому же принципу неизменяемых представлений, что уже используется в `Player.getHand()`/`Scoreboard.snapshot()`.

4. **Читаемость `finishRound()`**: метод смешивает определение проигравшего, обработку выбывания, передачу хода дилеру и завершение партии — разбить на именованные шаги (`resolveLoser()`, `advanceDealer(loser)`, `endGameIfDone()` и т.п.), каждый маленький и с одним смыслом.

5. **Проверка UI-портов (`console`, `desktop-libgdx`, `android`)** на предмет того, что они не реализуют собственную копию каких-либо игровых правил или логики выбора хода — если найдётся дублирование, вынести общую часть в `core` и обновить порты, чтобы они использовали её.

6. **Плюс все находки из Задания 1**, не попавшие в явный список выше — включить в общий план с указанием файла/класса и предлагаемого решения.

**Требования к результату Задания 4:**
- Сначала — документ `docs/refactoring-plan.md`: упорядоченный список шагов, каждый — маленький, поведение-сохраняющий коммит, с описанием "было/стало" и явной оценкой риска.
- Затем (если заказчик подтверждает) — пошаговая реализация: один коммит на шаг, после каждого коммита прогоняются **все** тесты, включая golden/replay-тесты из Задания 3 — они и есть страховочная сетка, которая должна поймать любое случайное изменение игровой логики в процессе рефакторинга.
- Рефакторинг не должен менять публичное поведение (`playGame`, `GameDriver`, сохранение/восстановление, события) для существующих UI-портов, кроме случаев, явно согласованных как breaking change.
